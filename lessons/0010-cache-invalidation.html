02 / EXPLORE

Follow the mechanism.

Invalidation makes an existing cache entry unavailable for reuse. It must be coordinated with the state change it represents.

Writer deletes the old entry too earlyThe database still exposes the old committed value.
A reader misses and fills from the old sourceThe cache has a live but soon-to-be-stale value again.
Writer commits the new valueThe refilled cache survives, so the next hit still returns the old value.

For this ordering problem, invalidate after a successful commit, not merely after issuing an UPDATE. A transaction can still roll back. Frameworks may offer an after-commit callback; the exact API depends on the framework. 

# Pseudocode: the callback runs only after a successful commit.
with database_transaction():
    update_product(...)
    on_commit(lambda: cache.delete(product_key))

In the repaired scenario, the next miss reads the newly committed source. On rollback, the committed source remains unchanged and the after-commit callback does not run.

This fixes the illustrated ordering bug, not every consistency problem. An older in-flight read can complete late; invalidation can fail after commit. A callback failure does not automatically roll back an already committed database transaction. Stronger coordination or durable recovery is a later depth topic.

Make the experiment your own

  1. Choose the ordering bug. Predict each next event and step until the final read. Record both source and cached values.
  2. Choose deletion after commit. Identify exactly which order changed and inspect the next read.
  3. Choose rollback. Check that the source stayed unchanged and no after-commit invalidation ran.
  4. Describe one controlled assertion for an agent's repair. Check the returned value, not just whether a delete method was called.
  5. State what you would investigate if the cache delete failed after commit.

This is one public product key. Retain authorization and user/tenant/query isolation when applying invalidation to private data.
