Code rollback and data recovery solve different problems. Reverting an application can stop a bad behaviour, but it does not restore rows that were already deleted. A migration can also leave the old code incompatible with the changed schema.

Make the recovery boundary explicit before changing data. Which schema versions can each application version read? What backup or point-in-time recovery exists? Which later writes would be lost by restoring a snapshot? A safer migration often separates adding compatible structure, switching usage, and removing old structure later.

The exercise takes a real SQLite backup, adds a later synthetic write, deletes the live rows, and restores into a separate disposable database. It checks row IDs and a business total. This proves more than merely checking that a backup file exists. The restored snapshot still lacks the post-backup write.

A recovery point concerns how much recent data loss is acceptable; a recovery-time goal concerns how long recovery may take. Those are product/operational decisions, not numbers this tiny exercise establishes. Verify a restore and reconcile later work instead of assuming a backup or rollback command is enough.
