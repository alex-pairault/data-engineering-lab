An origin is a scheme, host, and effective port. Paths do not change it. https://app.example.test/a and /b share an origin; a different host or port creates another. HTML supplies document structure, CSS styles it, and JavaScript can request data and update the DOM. These roles are separate from the API server.

The browser's same-origin policy restricts how scripts access other origins. CORS lets a server declare permitted cross-origin response access. A simple cross-origin GET can reach a server even when the browser refuses to expose its response to page JavaScript. For a request requiring preflight, the browser first sends OPTIONS; a denied preflight prevents the actual request.

Credentialed CORS needs an explicit permitted origin and the appropriate credential settings; wildcard Allow-Origin does not work with credentials. CORS is not authentication, authorization, or a complete CSRF defense. A command-line HTTP client is not governed by the browser's response-access policy. Debug the browser console and network request separately from the server's observations.

The downloadable probe runs two real loopback origins. It deliberately supplies permission on one route and omits it on the other. No login, cookies, outside service or production API is involved. Both simple GETs should appear in its terminal, while only one response is readable by the page.
