Follow the mechanism.

Storage checkinspect actual effects

A test boundary states which behaviour and dependencies a check actually exercises. A unit test can verify a pure function without storage or HTTP. An integration test can verify an application operation using a disposable database. The runner's name does not determine the boundary; inspect what is real and what is substituted.

Suppose the order rule rejects quantity zero and computes a valid total. A unit check can prove those cases. It cannot prove that the SQL column exists or that a rejected operation leaves storage unchanged. A permissive mock saying “save succeeded” does not execute your schema or transaction.

The browser illustrates a domain rejection followed by an incorrect write. The downloadable exercise uses a changed defect: the calculation passes, but INSERT targets a nonexistent column. Both demonstrate why checking the calculation alone misses a storage-boundary failure. The repaired operation also tests that invalid input adds no row.

Choose a small set of cases that can reject the wrong behaviour: a valid operation, an invalid input, and the relevant side effect. Assert returned values and stored state, not only that a method was called. Tests also have limitations; passing this fixture does not establish every production integration.
