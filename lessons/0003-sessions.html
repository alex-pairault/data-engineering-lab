A session has two sides

Connect a browser-held identifier to server-held identity and validity, then investigate tampering and expiry.

02 / EXPLORE

Follow the mechanism.

HTTP requests are separate exchanges. This lesson models one common way to recognise a signed-in user across them: an opaque session identifier backed by server-side state.

Browser: carries a reference

A cookie transports a session identifier on matching requests. Its presence is not proof, by itself, that the session is valid or that a user may read a resource.

Server: keeps the meaning

The application looks up the identifier, checks the authenticated session and validity, and uses the server-held identity for later permission decisions.

In this model, editing an extra browser field to claim another user_id does not change the identity in the server record. Guessing a new identifier must not create someone else’s authenticated session. Real identifiers need to be unpredictable.

Expiry exists on both sides

The browser may stop sending a cookie after its expiry. Separately, the server must enforce session validity, including timeout and revocation. A browser cookie can still exist after the server has rejected its session.

Logout must affect server state. Removing one cookie alone does not invalidate a copied identifier. In this model, logout invalidates the server session as well. Closing a browser is not a reliable server-side logout mechanism.

Cookie, session, and sessionStorage are different concepts

A cookie is a browser/server transport mechanism. A server-backed session is a state/identity design. The browser’s sessionStorage is a JavaScript storage API; it is not automatically the application’s server session. Token-based session architectures also exist and require their own validation rules.
