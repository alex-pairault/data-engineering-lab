An Airflow DAG expresses tasks and dependencies for a run. Task states describe execution progress. A task that fails its first attempt can enter a retry path when retries are configured; retries=1 permits one additional attempt, or two attempts in total.

The prepared DAG extracts [2, 3], deliberately fails transform on its first attempt, then transforms to total 10 on retry. The dependent verify task waits for successful upstream completion and asserts that total. TaskFlow passes these small values; it is not a pattern for moving large datasets through task metadata.

Retries do not undo external side effects. If a task writes before failing, a later attempt can write again. Use an idempotent sink or appropriate transactional/reconciliation design. Clearing a task instance, creating a new run and backfilling are distinct recovery operations; they do not simply reverse business effects.

The downloadable Airflow 3.3.2 exercise uses a separately prepared Python 3.12 environment and matching official constraints. It initializes only an isolated AIRFLOW_HOME and runs dag.test() from the configured DAG folder. This is real local serialized task execution, not a production distributed-executor, scheduler or UI verification. Installation belongs before the timed lesson.
