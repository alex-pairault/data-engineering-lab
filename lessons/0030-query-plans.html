N+1 describes one query for N parent rows followed by one child query per parent. Five parents create six SELECTs in this example. Latency can grow with parent count even when each individual query looks small.

Fetch children for a bounded set of parents together, then group them by parent. The exercise verifies equal totals while reducing six SELECTs to two. Bound batches and retained results as well: fewer round trips do not justify unbounded memory or a huge response.

A query plan describes how the database intends to execute a statement. The real SQLite exercise prints its filter plan before and after an index and verifies identical results. Plan text can change by database version. PostgreSQL cost estimates are not milliseconds; EXPLAIN ANALYZE executes the statement, which matters for writes.

An index can help selected access paths but adds storage and write costs and does not guarantee improvement for every query. Measure a relevant workload, inspect row counts and conditions, and avoid claiming a speedup from a plan label alone. This lesson counts operations and checks results; it does not invent timing evidence.
