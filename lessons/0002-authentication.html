02 / EXPLORE

Follow the mechanism.

Authentication establishes identity. Authorization decides whether that identity may perform a particular operation. A successful sign-in does not settle every later permission question.

Check a submitted secret

For password sign-in, the server uses a vetted verification function to check the submitted password against a stored salted password hash.

Protect the stored verifier

Use a dedicated password-hashing scheme through an established library. Passwords are not normally stored using reversible encryption or a plain fast hash such as SHA-256.

A password hash is used to check a candidate, not to recover the original password. Salting and an appropriately expensive password-hashing scheme make guessing harder; they do not make weak passwords impossible to guess. 

# Illustrative PHP-style decision; use established APIs.
if password_verify(submitted_password, stored_hash):
    accept_identity(account.id)
else:
    reject_sign_in()

A second factor is a different kind of evidence

A password is something you know. A security key is something you possess. Two knowledge secrets, such as a password and PIN, do not by themselves constitute two distinct factor types. MFA helps protect sign-in; resource permissions and session protection still matter afterward.

What belongs in a real sign-in design?

Server-side verification, secure transport, safe password storage and recovery, rate limits, and appropriate MFA. Choose a framework or provider’s maintained implementation. This lesson explains the boundary rather than building an identity provider.
