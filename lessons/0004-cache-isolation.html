Trace two identities through a shared cache and verify isolation on both cache misses and hits.

02 / EXPLORE

Follow the mechanism.

A cache reuses a previously obtained value. Its key decides which requests are treated as asking for the same result.

Suppose a note list depends on the authenticated user. A constant key such as notes treats every user’s list as the same value. The first user can populate it with private data that a later user receives. 

cached = cache.get("notes")
if cached is not None:
    return cached   # Which user's data is this?

notes = database.notes_for(user.id)
cache.set("notes", notes, ttl=60)
return notes

The filtered database query only helps on the path that executes it. Follow the early return on a cache hit as carefully as the cache-miss path.

Key the changing context

For this fixed-permission example, derive both reads and writes from the authenticated user: notes:{user.id}. Never let an arbitrary caller choose the trusted identity.

Keep authorization in the decision

A user-specific key is not a permission check. Real designs must also respect changing access, tenants, filters, and any other context affecting the value.

Browser HTTP caches and application caches are separate mechanisms. Disabling the browser HTTP cache does not clear a server-side Redis or in-process application cache.
