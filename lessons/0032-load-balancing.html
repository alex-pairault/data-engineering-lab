02 / EXPLORE

Session storeexpiry / revocation

A load balancer routes requests across application instances. Those processes do not automatically share memory or local files. A browser-held session identifier is only useful if the selected instance can resolve and validate the corresponding state.

With sessions stored only on A, requests reaching B can fail authentication. Affinity can keep a user on A and reduce the symptom, but it does not replicate or make A’s state durable. If A disappears, the local session can disappear with it.

A shared session store can let both replicas observe validity and revocation. Its availability, expiry policy, ownership checks and private cache boundaries still need design. Adding replicas does not remove those responsibilities. Resource limits and worker counts also affect memory and throughput, connecting back to the hardware lesson.

Kubernetes can manage workloads and a Service can offer stable access to changing backends. It does not automatically replicate your application’s sessions, files or database contents. This session needs a correct role distinction and a failure trace, not a cluster installation or specialist administration.
