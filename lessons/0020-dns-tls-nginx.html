02 / EXPLORE

Follow the mechanism.

DNSresolve host
→
TLS → Nginxverify peer; handle HTTP
→
Application upstreamseparate connection

Trace the boundaries in order. DNS resolves a name to an address. The client connects and performs TLS for HTTPS, checking the requested identity and trust chain. Nginx then handles HTTP and may forward to an application upstream on a separate connection.

A DNS answer proves neither certificate validity nor application health. A certificate identity mismatch can prevent a valid HTTPS exchange. Do not treat bypassing verification as a repair. When TLS terminates at Nginx, the upstream connection has its own protocol and protection requirements.

In the controlled upstream-refusal case, the client reaches Nginx but its HTTP application peer is unavailable. Nginx returns 502, and the relevant error log identifies the refused upstream address. Real 502s have other causes, including protocol or response problems, so the status is a starting observation.

The downloadable local stack uses HTTP proxy_pass to a Python HTTP server. PHP-FPM commonly needs FastCGI forwarding with fastcgi_pass; those protocols are not interchangeable. The local stack does not configure public DNS or TLS, and therefore does not verify those production boundaries.
