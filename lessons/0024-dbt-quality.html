A dbt SQL model transforms data and can describe its grain. The prepared model returns one row per customer who has a paid source order. Customers with no paid order are outside this model’s explicit scope; the earlier outer-join lesson showed how a different requirement changes that design.

Data tests query for violations in existing data. Default success means zero failing rows, unless configuration changes severity or thresholds. Built-in tests include not_null, unique, relationships and accepted_values. They are different from dbt unit tests and from database constraints that govern future writes.

Test source or staging assumptions before filters and aggregation can hide bad records. A duplicate source ID may disappear from an aggregate while still corrupting its total. Relationships and accepted_values do not substitute for not_null. The singular negative-amount test also needs a separate null assertion.

The downloadable local project uses tiny CSV seeds and a file-backed DuckDB profile across separate commands. It pins a selected dbt/adapter/runtime snapshot. Prepare the environment before the lesson; no Snowflake account or credentials are required. Inspect actual test failures and restore the fixture after each deliberately planted defect.
