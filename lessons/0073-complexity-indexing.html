02 / EXPLORE

One mechanism to use today.

→
Totals indexone value per customer key
→
n requested customersexpected constant lookup each

A straightforward report scans all m orders for each of n customers, doing n × m order visits. Build a dictionary of paid totals in one order pass, then answer each customer from that index. Under ordinary fixed-size-key hashing, expected total work is O(m+n).

Building the index is not free. It takes expected O(m) work and retains O(u) entries for u distinct paid customer IDs. The returned result additionally stores up to n distinct customer totals. For a single tiny query, extra setup may not pay off; repeated queries and larger inputs can change that tradeoff.

Preserve behaviour while optimizing: accumulate repeated legitimate orders, ignore pending amounts, retain requested customers with total zero, and avoid mutating input. An operation-count experiment supports the chosen implementation on tested inputs; it does not automatically prove every possible complexity claim. 

# Repeated scan: n customers × m orders.
for customer in customers:
    for order in orders:
        ...
# Index once, then look up each customer.
for order in orders:
    ... # accumulate by customer ID
for customer in customers:
    ... # read its total
