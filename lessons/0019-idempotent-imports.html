Replayappend or UPSERT

An operation is idempotent when repeating it preserves the intended business effect. Attempt counters and responses may differ. For a snapshot import, stable source identity lets the database recognize that a row was already applied.

The source contains A=10, B=20 and C=30. A partial run commits A and B. Blindly appending the full input on replay stores five rows. A unique external ID with an explicit UPSERT stores three rows totaling 60. Generating a new random identity on each attempt defeats this protection.

Define what reused identity with changed content means. This snapshot contract updates B from 20 to 25, making the total 65. An immutable event contract might reject that change instead. Do not substitute broad “ignore every error” handling, and do not assume SQLite INSERT OR REPLACE has the same update semantics: it can delete and reinsert a conflicting row.

When applying an event identity and a business effect, commit them atomically. A retry-safe database import does not establish exactly-once external payments or messages. Place the retry boundary around the operation whose effects you can identify and verify.
