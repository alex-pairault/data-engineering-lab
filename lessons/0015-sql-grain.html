02 / EXPLORE

Follow the mechanism.

Grain states what one row represents. Here orders contain one row per order; lines contain one row per line; payments contain one row per payment. A primary key identifies a row, but a surrogate ID alone does not enforce every business uniqueness rule.

3 payment rows30, 30 and 40

A join returns every matching pair. Joining both child collections by order ID makes two times three rows for order 901. Each line repeats three times, and each payment twice. Grouping afterwards returns one row per order, but the sums are already inflated: 300 for lines and 200 for payments, rather than 100 each.

SUM(DISTINCT amount) is not a general repair. It removes equal values, not duplicated business rows. Two legitimate lines both cost 50, and two payments are 30. DISTINCT reduces those totals to 50 and 70. A paid zero and repeated legitimate amounts are useful edge cases.

Preaggregate each child to one row per order before joining those results. Now each total appears once. LEFT JOIN and COALESCE also keep orders with no child total, connecting to lesson 8. Other query designs can work; the requirement is the intended row meaning and correct values.

Constraints protect different assumptions: a primary key rejects duplicate row IDs; a non-null foreign key rejects an unknown parent; a CHECK can reject a negative amount. A foreign key does not restrict an order to one line. For one child per order you would need an additional uniqueness rule consistent with the business. In SQLite, enable foreign-key enforcement for each connection; the exercise does so.
