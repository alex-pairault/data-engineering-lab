02 / EXPLORE

Follow the mechanism.

An agent’s completion message is a claim. To accept a change, connect that claim to an observable requirement and evidence.

State the ruleEach signed-in user may receive only their own private note list.
Challenge the boundaryUse a second identity after the first identity has warmed shared state.
Observe a meaningful failureThe check should reject the faulty implementation for the expected reason.
Verify the changed behaviourRun the same check against the repair and inspect what changed in the diff.

A one-user happy-path check can pass on both the buggy shared-key version and the repaired user-specific version. More test output does not automatically mean more useful coverage. 

# Example shape of a behavioural check:
clear_shared_cache()
request_as(first_user)
result = request_as(second_user)
assert every_item_belongs_to(result, second_user)

This is a test shape, not evidence that a real service was tested. A real end-to-end test needs distinct authenticated browser contexts, suitable data, and the shared backend/cache state under test. Two tabs sharing one login may still represent the same user.

Ask the product question too

Agree how old the information may be, which changes must appear immediately, and how to measure the speed improvement. A cache can satisfy an isolation check while still violating a freshness requirement.

Make the experiment your own

  1. Run the default one-user case. Explain what it does and does not establish.
  2. Choose cases that cross the user boundary in both request orders.
  3. Run the same selected assertions against the two implementations. Identify the check that rejects the buggy one.
  4. In your explanation, write a short Given/When/Then test and a concrete freshness question for the product owner.
  5. Describe the evidence you would ask an agent to provide: actual diff, commands, results, and remaining limitations.
