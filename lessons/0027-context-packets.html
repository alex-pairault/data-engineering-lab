A context packet is a bounded task description for an agent or colleague. Here it is a teaching pattern, not a standard or a guarantee of obedience. Its purpose is to make the requested change and its evidence reviewable.

Start with the user problem and smallest useful change. Add relevant files and current behaviour, the invariant that must remain true, acceptance cases, the verification command, and a stop condition. Explain why constraints matter; do not rely on the agent guessing ownership, retry or compatibility rules.

More text is not automatically better context. An unrelated repository dump can obscure the important boundary. Provide focused sources, label facts versus hypotheses, and keep the work small enough to inspect. Do not place credentials or employer-private data in a public learning task.

The example task is an order search change. It must preserve authenticated owner scoping on cold and warm paths, return required rows, and reject unknown input without a write. Ask for the diff and verification output, then independently inspect both. A good packet improves the chance of useful work; the resulting code still needs review.

Make the experiment your own

  1. Compare the vague, dump-only and bounded model packets. Identify what each fails to specify.
  2. Write a packet for one small change to the synthetic order example: problem, sources, invariant, cases, command and stop condition.
  3. Ask your teaching agent to implement only that scope in a disposable copy, or review the packet without implementation.
  4. Compare the result with the acceptance cases and explain one assumption that the packet did not resolve.
