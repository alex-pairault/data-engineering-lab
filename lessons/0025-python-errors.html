02 / EXPLORE

Follow the mechanism.

Callerdata or explicit error

An API call crosses several boundaries: transport, HTTP status, JSON parsing and application schema. Success at one does not establish success at the next. Valid JSON can have the wrong shape; a timeout can leave a write’s outcome unknown.

Use explicit timeouts and bounded policies. The prepared Python client retries a selected GET HTTP 503 once, classifies transport failure, and validates a small list-of-orders schema. It catches urllib HTTPError before its URLError base class. The injected transport is deterministic and sends no network request.

Do not turn failure into a success-shaped empty list. Preserve an error category and useful non-sensitive context so the caller can choose recovery. Catch specific failures rather than suppressing everything. A per-attempt timeout is not necessarily a deadline for an entire workflow or download.

Retry policy must account for side effects. After a POST timeout, the server may already have committed the operation. Blind retry can duplicate an effect; use the operation’s idempotency contract or reconcile its status. The local GET exercise does not claim a general retry framework.
