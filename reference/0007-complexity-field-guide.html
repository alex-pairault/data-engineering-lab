Start with n, not a formula.

n is an input size: for example, the number of items in a list. If two independent lists are involved, name both sizes n and m. A work unit might be one comparison, one item read, or one emitted value. State the unit and case before comparing counts.

O(1) means bounded work independently of the input size under the chosen model. O(n) is a linear bound. Big-O formally gives an eventual upper bound; it does not mean “exactly” and does not automatically mean “worst case”. Beginner questions here ask for the tightest usual growth family in the stated case. A linear algorithm is technically also bounded by O(n²), but that looser label hides useful information.

2ⁿ means multiplying 2 by itself n times. n! is factorial: 4! = 4 × 3 × 2 × 1 = 24. They count candidates here. Materializing each length-n candidate adds per-output work and retained output storage; candidate count is not automatically complete runtime. Constants also matter in practice: an O(n) approach with large fixed overhead can lose on small data. Benchmark representative inputs after reasoning about growth.

Six questions for unfamiliar code

  1. What is n? Name every independent input size.
  2. Which case? Early exit, worst case, expected behaviour, or an amortized sequence?
  3. What costs one unit? Identify reads, comparisons, copies, calls, or other chosen work. State small-key/number assumptions.
  4. How often does it repeat? Add sequential phases; multiply genuinely nested input-sized work; track shrinking or growing bounds.
  5. What is hidden? Include membership scans, sorting, slicing, hashing/equality costs, and preprocessing. Then keep the dominant term.
  6. What stays live? Separate retained input, auxiliary state (including recursion), and returned or consumer-retained output.

For example, two separate n-item scans do 2n work → O(n). An n loop with a fixed three-step inner loop does 3n → O(n). n independent customers each scanning m orders do nm → O(nm). A triangular n(n−1)/2 pair loop still grows as O(n²).

Python operations you need to inspect

Ordinary CPython list/hash-table model with small fixed-size keys and constant-cost equality. Bounds concern growing container size; custom operations can change them.
Operation Typical bound Condition or hidden cost
len(a_list) O(1) List length is stored; not a full scan.
a_list[i] O(1) Known valid integer index in a list, not generic sequence access.
x in a_list O(n) worst case Missing or late match; equality cost assumed bounded.
a_list[:k] O(k) time + result space Copies references; does not deep-copy nested values.
a_list.append(x) Amortized O(1) A resizing call can take O(n); the sequence-average cost is bounded.
a_list.pop() Amortized O(1) Remove from the end; storage management can have occasional larger costs.
a_list.pop(0) O(n) Shifts remaining references.
deque.popleft() O(1) A queue-oriented operation; arbitrary middle access has different costs.
x in a_set / key in a_dict Expected O(1) Ordinary hashing; collision-heavy lookup can degrade toward O(n).
x in a_dict.values() O(n) worst case Searching values is a scan, not a hash lookup by key.
set(a_list) Expected O(n) Build cost and up to O(n) entries; not free preprocessing.
sorted(items) O(n log n) worst-case comparisons Creates a result list; existing order can help. Key/comparison costs still matter.
bisect search O(log n) Already sorted random-access list; insertion into the list remains O(n).
sum(values) O(n) in this numeric model One call hides a full iteration. Arbitrary-size integer arithmetic can add cost.

Three different meanings of “average”

Worst-case: an upper bound for the most costly input of that size in the stated model. A missing target in a list requires a full scan.

Expected/average: cost under distribution or hashing assumptions. Ordinary dict/set lookup is expected constant time under suitable assumptions; a pathological collision pattern can be worse.

Amortized: total cost spread across a sequence of operations, without assuming random input. Occasional list resizes can be expensive while a sequence of appends has amortized O(1) per append.

These are not interchangeable labels. Big-O can describe any of these cost functions when the case is specified.

Memory: count what remains at once

An eager list retains its output; a running accumulator keeps only working state. A lazy producer may have constant auxiliary state while the consumer retains every value. A seen set grows with distinct values even inside a generator. Recursion retains active stack frames.

Example Auxiliary state New retained output
Running total with small numbers O(1) One scalar
Return n transformed values in a list O(1) beyond output for a direct loop O(n)
Lazy transform without accumulation O(1), excluding upstream state Depends on the consumer
Exact set-based duplicate detection O(n) in the all-distinct case One boolean

Turn a label into evidence

python tools/check.py --complexity 01
python tools/complexity_probe.py 01
# After your own attempt:
python tools/check.py --complexity 01 --reference

Use sizes 8 and 32, predict the operation counts, run, and explain why they changed. Add one case not in the prepared tests. Counter experiments examine concrete paths and chosen operations; a handful of inputs cannot prove an asymptotic bound by themselves. Passing functional tests also does not guarantee an efficient algorithm.

Bring your code and reasoning to your teaching agent. An honest explanation can say: “n is the number of orders. I scan them once, doing expected constant-cost dict updates for small keys, so expected time is O(n). The dictionary keeps u distinct customer totals, using O(u) auxiliary entries.”
